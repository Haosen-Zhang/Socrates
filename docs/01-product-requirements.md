# Socrates 产品需求文档

## 1. 产品定位

Socrates 是一个面向代码、科研、写作和复杂决策的多模型群聊式 Agent 工作台。

用户可以把 OpenAI、Anthropic、DeepSeek、Gemini、Qwen、Kimi、GLM、Ollama 等不同来源的模型放进同一个任务房间，并像微信群聊一样让它们按设定规则讨论同一个问题。

Socrates 的差异点是：模型不是简单的下拉选项，而是带角色、权限、任务职责和发言策略的群成员。

## 2. 核心价值

单模型 Agent 的常见问题包括：过度自信、遗漏边界条件、风格单一、代码审查不足、长任务中缺少反驳机制。

Socrates 希望利用不同模型的能力差异形成结构化审稿机制：一个模型提出方案，一个模型质疑风险，一个模型补充实现细节，一个模型最终裁决和执行。

核心价值包括：

- 多模型互补：利用不同模型在代码、推理、写作、审查、中文、长上下文等方面的差异。
- 可控讨论：用户可以控制发言顺序、轮数、角色、预算和最终执行者。
- 审稿优先：默认先讨论、批判、修正，再执行。
- 执行可审计：执行前展示计划、diff、命令和风险，用户可以确认。
- 本地优先：优先作为桌面工作台运行，项目文件和 API Key 默认留在本地。

## 3. 目标用户

### 3.1 开发者

用于代码审查、架构设计、复杂 bug 排查、重构方案比较、测试计划生成、自动 patch 生成。

### 3.2 科研人员

用于论文思路讨论、实验设计、代码实现审查、数据分析流程规划、文献观点对照、审稿意见模拟。

### 3.3 写作者和研究型用户

用于观点辩论、文章提纲、逻辑漏洞审查、多风格润色、长文总结和反方论证。

### 3.4 高阶 AI 工具用户

已经使用 OpenCode、Claude Code、Crush、Kilo Code、Cursor、Aider 等工具，但希望引入多模型审查和可控编排。

## 4. 核心概念

### 4.1 Model Provider

模型供应商，例如 OpenAI、Anthropic、DeepSeek、Google、Moonshot、Zhipu、Qwen、Ollama、vLLM。

### 4.2 Model

供应商下的具体模型，例如 GPT-5.5、Claude Opus 4.8、DeepSeek V4 Pro。

### 4.3 Agent

进入房间的 AI 成员。Agent 不等于模型，它由模型、角色、系统提示词、工具权限、发言风格和预算限制组成。

### 4.4 Room

一次任务或长期项目的讨论空间。Room 类似微信群聊或 Discord channel，可绑定项目目录、文档集合、历史记忆和群公告。

### 4.5 Orchestration Policy

群聊编排策略，定义谁先说、谁反驳、讨论多少轮、是否投票、谁总结、谁执行。

### 4.6 Shared Blackboard

共享黑板。所有 Agent 可读取的结构化中间状态，用来记录目标、候选方案、问题列表、风险、决策、待执行操作。

### 4.7 Final Executor

最终执行者。可以是一个具备写文件、运行命令、生成 patch 权限的 Agent，也可以是只负责输出总结的 Agent。

## 5. 核心用户流程

### 5.1 创建模型和 Agent

用户添加 API Key，选择模型，创建 Agent，并为 Agent 设置角色和权限。

示例：

- Claude Opus Agent：架构审稿人，只读权限，擅长发现逻辑漏洞。
- GPT Agent：总设计师和执行者，可写文件、可运行命令。
- DeepSeek Agent：实现细节审查者，可读文件、生成 patch 建议。

### 5.2 创建 Room

用户创建一个 Room，选择项目路径，邀请多个 Agent，设置群公告和任务规则。

Room 可以是一次性任务，也可以是长期项目空间。

### 5.3 发起任务

用户输入需求，例如：

```text
请讨论这个 MRI reconstruction repo 的 VAA 模块设计，重点检查 qkv、config、ssim_spatial_dims auto、slab/slice 模式是否一致。讨论 6 轮，最后由 GPT-5.5 总结并提出 patch。
```

### 5.4 多模型讨论

Orchestrator 根据策略组织发言。

典型流程：

1. Architect Agent 给出初始方案。
2. Reviewer Agent 找漏洞和风险。
3. Implementer Agent 补充实现细节。
4. Architect Agent 修正方案。
5. Reviewer Agent 复核。
6. Final Executor 总结并生成执行计划。

### 5.5 用户确认执行

如果任务涉及文件修改或命令执行，Socrates 先展示执行计划、文件 diff、命令和风险说明。

用户确认后才真正执行。

## 6. 功能需求

### FR-001 模型供应商管理

系统应支持添加、编辑、删除模型供应商配置。

必须支持：

- API Key 或本地 endpoint 配置。
- Base URL 配置。
- 默认模型配置。
- 模型能力标记，例如上下文窗口、是否支持工具、是否支持流式输出、是否支持视觉。
- 连接测试。

首批建议支持：OpenAI-compatible API、Anthropic、DeepSeek、Google Gemini、Ollama。

### FR-002 Agent 管理

系统应支持基于模型创建 Agent。

Agent 配置包括：

- 显示名称。
- 绑定供应商和模型。
- 角色描述。
- 系统提示词。
- 发言风格。
- 工具权限。
- 温度、最大 token、预算限制。
- 是否可作为最终总结者。
- 是否可作为最终执行者。

### FR-003 Room 管理

系统应支持创建、编辑、删除 Room。

Room 配置包括：

- 房间名称。
- 绑定项目路径。
- 邀请的 Agent 列表。
- 群公告和任务规则。
- 默认编排策略。
- 默认上下文范围。
- 历史消息保留策略。

### FR-004 群聊式消息界面

系统应提供类似 WeChat 的群聊界面。

界面应清晰展示：

- 用户消息。
- 每个 Agent 的头像、名称、模型来源和角色。
- 当前轮次。
- 发言顺序。
- 正在思考或流式输出状态。
- 引用的上文或文件上下文。
- 工具调用和执行结果。
- 最终总结和行动计划。

### FR-005 编排策略

系统应支持至少四种基础策略：

- Round Robin：固定顺序轮流发言。
- Debate：方案、反驳、修正、复核。
- Review Board：多个专家角色并行或顺序审查。
- Pipeline：Draft、Critique、Revise、Verify、Execute。

每种策略都应支持：

- 最大轮数。
- 最大预算。
- 发言顺序。
- 最终总结者。
- 最终执行者。
- 是否需要引用前文。
- 是否需要输出结构化字段。

### FR-006 上下文构建

系统应根据任务和 Room 配置构建上下文。

上下文来源包括：

- 当前对话历史。
- 项目文件。
- 用户手动选择的文件。
- 搜索结果。
- 共享黑板。
- Agent 私有记忆。
- Room 历史决策。

系统应在 UI 中提示本轮发送给模型的关键上下文摘要。

### FR-007 共享黑板

系统应维护一个结构化共享黑板。

黑板字段建议包括：

- task_goal：任务目标。
- constraints：约束。
- assumptions：假设。
- findings：发现的问题。
- proposals：候选方案。
- critiques：反驳和风险。
- decisions：已确认决策。
- action_plan：行动计划。
- pending_questions：待确认问题。
- execution_artifacts：待执行 patch、命令、文件变更。

### FR-008 工具调用

系统应支持工具调用能力，但 MVP 可以先只支持只读工具。

工具类型包括：

- 文件读取。
- 文件搜索。
- Git diff。
- 文件修改。
- 终端命令。
- 测试运行。
- 浏览器搜索。
- MCP 工具。
- Notebook 或 Python worker。

### FR-009 执行审批

任何写文件、删除文件、运行命令、网络请求、安装依赖、Git 操作都应进入审批流程。

审批界面应展示：

- 操作类型。
- 影响范围。
- diff 或命令。
- 发起 Agent。
- 相关理由。
- 潜在风险。

### FR-010 成本和预算控制

系统应跟踪 token、费用、轮数和模型调用次数。

用户应能设置：

- 单任务预算。
- 单 Room 每日预算。
- 单 Agent 预算。
- 达到预算后的行为，例如停止、询问、降级模型。

### FR-011 历史记录和可追溯性

每次任务应可回放。

系统应保存：

- 用户输入。
- 编排策略。
- 每轮模型输入摘要。
- 每轮模型输出。
- 黑板变化。
- 工具调用。
- 用户审批记录。
- 最终结果。

### FR-012 模板系统

系统应支持 Room 模板和 Agent 模板。

默认模板建议包括：

- Code Review Room。
- Architecture Debate Room。
- Paper Review Room。
- Experiment Planning Room。
- Writing Critique Room。
- Bug Triage Room。

## 7. 非功能需求

### NFR-001 安全

API Key 必须安全存储。文件写入、命令执行、网络访问必须受权限和审批控制。

### NFR-002 隐私

默认本地优先。项目文件不应发送给未参与当前任务的模型。系统应清晰提示哪些内容会发送给哪些供应商。

### NFR-003 可扩展性

新增模型供应商、工具、编排策略时不应修改核心 UI 和核心执行逻辑。

### NFR-004 可观测性

系统应记录任务 trace、token 统计、错误、重试、工具调用和审批记录。

### NFR-005 跨平台

桌面端应优先支持 macOS，后续支持 Windows 和 Linux。

### NFR-006 可靠性

模型请求失败时应支持重试、跳过、替换模型、暂停任务、继续任务。

### NFR-007 性能

UI 应支持流式输出。长对话和长文件上下文应使用摘要、检索和裁剪策略控制上下文大小。

## 8. MVP 范围

MVP 目标是验证“多模型群聊讨论”是否真的比单模型更有用。

MVP 应包含：

- 添加 OpenAI-compatible 和 Anthropic API Key。
- 创建 Agent。
- 创建 Room。
- 设置 2 到 4 个 Agent。
- 设置发言顺序、轮数、最终总结者。
- 群聊式展示流式输出。
- 支持 Round Robin 和 Debate 两种模式。
- 输出 final summary 和 action plan。
- 保存本地历史。

MVP 暂不包含：

- 自动修改文件。
- 终端命令执行。
- MCP 插件系统。
- 多设备同步。
- 团队协作。
- 复杂向量检索。

## 9. V1 范围

V1 应在 MVP 基础上加入项目工作台能力。

建议包含：

- 项目路径绑定。
- 文件搜索和只读上下文。
- Git diff 查看。
- 生成 patch，但需要用户确认。
- Review Board 和 Pipeline 模式。
- Shared Blackboard UI。
- 成本统计。
- Room 模板。

## 10. V2 范围

V2 可以向完整 Agent IDE 演进。

建议包含：

- 受控文件写入。
- 受控命令执行。
- 测试运行。
- MCP 工具集成。
- 本地向量索引。
- Agent 私有记忆。
- 团队共享 Room。
- 云端备份和同步。

## 11. 成功指标

产品验证指标建议：

- 用户是否愿意在复杂任务中使用 2 个以上模型。
- 多模型讨论后用户采纳率是否高于单模型回答。
- 代码任务中 patch 被接受比例。
- 讨论轮数和结果质量之间的关系。
- 用户是否复用 Room 模板。
- 用户是否为更高质量讨论接受更高 token 成本。

## 12. 关键开放问题

- 多模型讨论的默认轮数应该是多少，才能兼顾质量和成本。
- 是否需要“主持人 Agent”来动态决定下一个发言者。
- 是否需要让模型互相看到完整原文，还是只看摘要和黑板。
- 最终执行者是否必须是同一个模型，还是可以由多个模型分别生成 patch 和 review。
- API Key 和本地项目隐私提示如何做到足够清晰但不打扰用户。
